# 2026-09-11 配信の描画が 1fps になる件

9/10 の配信が 0.1〜1.9fps の止まった絵を14分流し、9/11 は描画ゲートが 1.9fps を
捕まえて中止になった。その切り分けと対処の記録。

## 結論

**原因は2つあり、どちらも「GPU が1枚しかないのに X サーバが2つある」ことに由来する。**

1. **`:99` は gdm より後に起動していないと描画を締め出される。** GPU が空いていても
   1.0fps に固定される。gdm を止めると同じ `:99` が 56,142fps を出す。
2. **NoScanout の `:99` には表示クロックが無いので、vsync を待つと 1fps に見える。**
   これは描けていないのではなく、来ない vblank を待っているだけ。

対処は `setup/reset_display.sh` と `bottan-live-display.service`。配信の直前に `:99` を
作り直し、`__GL_SYNC_TO_VBLANK=0` を渡した glxgears で実測してから配信へ通す。
Unity にも同じ環境変数を渡す（`live/unity_live.py`）。

## 実測

すべて同じ晩（2026-09-11 21:00〜22:05）、同じホスト、同じ GPU。

| 条件 | `:99` の glxgears |
|---|---|
| EDID スキャンアウト / vsync あり / gdm 起動 | 1.0〜1.4fps |
| EDID スキャンアウト / vsync なし / gdm 起動 | 1.0〜1.4fps |
| EDID スキャンアウト / vsync なし / gdm 停止 | 67,482fps |
| NoScanout / vsync なし / gdm 停止 | 56,142fps |
| NoScanout / vsync なし / gdm 起動（`:99` は gdm より前に起動） | 1.0fps |
| NoScanout / vsync なし / gdm 起動（`:99` を gdm の後に作り直す） | 59,485fps |

最後の行が対処の根拠。**`:99` を作り直すだけで、デスクトップを残したまま共存できる。**

## 外れた仮説

同じ罠に戻らないよう、潰した順に残す。

### `:0` も 1〜2fps だからホスト全体の故障

**違う。ロックされた X11 セッションの GL は正常時も進まない。** `:99` が 60fps で
健全なときに `:0` で測ると、13秒で1フレームも進まなかった。`loginctl` は
`Active=no LockedHint=yes`（21時間アイドル）を返していた。無人運用の 21:00 に画面は
ロックされているので、**`:0` の fps は判定に使えない。** 9/10 の調査はこれを根拠の
一部にして「ホスト全体の表示経路が停止」と読んでいたが、誤りだった。

### ドライバ 595.84 が Blackwell で壊れている

**違う。ドライバ版は GPU 交換の前後で同一。** `/var/log/apt/history.log` によると
8/04 に 595.84 を入れ、8/29 22:37 の `apt purge *nvidia* cuda*` のあと 22:38 に
**同じ 595.84 を入れ直している**。3060 Ti で NoScanout が 60fps で回っていたのも
595.84。「動いていた版に戻す」という手は存在しない。

### ollama が GPU を食っているせい

**このときは違ったが、実際に起こりうるので必ず確認すること。** 22:00 の測定では
`nvidia-smi pmon` が `llama-server` の SM 使用率 87〜92% を示していて、
glxgears は 1fps だった。ただし GPU 使用率が 0% の瞬間を待って測り直しても
1.0fps のままで、これは無罪だった。**`nvidia-smi` の瞬間値ではなく `pmon` で
プロセス別に見ること。** 外部ホストからの `/api/chat` が常時走っている
（HANDOFF の 2026-09-02 の残件）。

### GPU の表示経路が謎に停止している

**言い方が不正確だった。** 9/10 の時点では「NVIDIA ドライバの表示経路が停止」と
書いたが、実際には `:99` が描画の配分から締め出されていた。GPU の計算も、
GL コンテキストも、レンダラ名も正常なまま起きる。

## 起動可否のほうの症状

描画が遅いのとは別に、**`:99` が起動すらできない**症状もある。

```
(EE) NVIDIA(GPU-0): Failed to acquire modesetting permission.
(EE) NVIDIA(0): Failing initialization of X screen
(EE) no screens found
```

これは `:99` が実スキャンアウトを持っていた 8/31〜9/11 の構成に固有。スキャンアウトを
持つと DRM master が要り、デスクトップ側が握っていると取れない。9/11 21:40 に
これで起動不能になり、`Restart=always` が5秒おきに叩き続けた（9/10 には
restart counter が 560 まで行っている）。`setup/reset_display.sh` はこのログ行を
見つけたら専用の文面を出し、リトライループも自分で止める。

NoScanout へ戻したので、この症状は構成上もう起きない。

## 経緯

`:99` に実スキャンアウトを持たせたのは 8/31 の `a109cff`。5070 Ti で NoScanout が
約1fps になるのを受けて、未使用端子 DFP-1 に実モニタの EDID を割り当てた。
1fps は直ったが、**vsync を切る選択肢は試されていなかった**。実スキャンアウトは
DRM master を要求するので、代わりにデスクトップとの競合が生まれた。

3060 Ti 時代（8/24〜8/28）は NoScanout でデスクトップと共存し、5晩とも丸一時間
60fps で完走している（サンプル50件超、最小 59.6 最大 60.1）。失ったのは性能ではなく、
共存できるという前提だった。

## 残件

- **デスクトップ側の描画を確かめていない。** `:99` を作り直したあと `:0` が正常に
  描けるかは未検証。測定時はロック画面で、ロック中の `:0` は元から進まないので
  区別がつかない。画面を解除して体感で見ること。
- **起動直後は `:99` が締め出されている可能性が高い。** `bottan-live-xorg.service` は
  `multi-user.target`、gdm も同じ頃に上がるので順序は保証されない。配信は
  `bottan-live-display.service` が毎晩作り直すので影響を受けないが、**起動直後に
  手で確かめると遅く見える。** そのときは作り直してから測ること。
